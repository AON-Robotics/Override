# OTOS odometry for autonomous

Override reads `O,<x inches>,<y inches>,<heading degrees>\n` from the V5 Brain's USB User Port through its odometry task. The RaspberryPi `otos_stream` app sends these packets at 50 Hz. Connect the Pi to the Brain's User Port (commonly `/dev/ttyACM1` on the Pi), and connect the OTOS to the Pi's I2C bus (commonly `/dev/i2c-1`). The Brain also samples its tracking wheels and V5 IMU every 20 ms.

On the Pi, build with `-DVEXPI_BUILD_VISION=OFF` if the camera SDK is unavailable, then run `otos_stream` before autonomous. Keep the robot still during startup IMU calibration. The app checks the OTOS, calibrates, resets tracking, and opens the serial port. It retries if the Brain is disconnected. Only one Pi program can own the User Port at a time; `red_tracker` and `otos_stream` cannot run concurrently on that port.

The Pi maps OTOS X right/Y forward/counterclockwise heading into Override X forward/Y right/clockwise heading. Override anchors the first received pose to the current Brain pose. A later `resetPose()` anchors all sensor baselines to the requested field pose. OTOS packets are stale after 300 ms. Autonomous and pose based motion continue using another working position source; they stop when every position source fails.

Position source priority is: tracking wheels plus OTOS (tracking wheel motion corrected toward OTOS position), tracking wheels alone, OTOS alone, then the differential drivetrain's motor encoders. Motor encoder distance uses `DRIVE_WHEEL_DIAMETER` and `MOTOR_TO_DRIVE_RATIO`; its turn estimate uses `DRIVE_WIDTH`. Motor odometry assumes the wheels do not slip, so it is a temporary fallback. The motor fallback is wired for the configured `DifferentialDrive`; the other chassis classes have no motor encoder fallback. Source changes rebase OTOS position to the current pose to avoid an immediate jump. The V5 IMU remains the preferred heading source; wheel or OTOS heading is used only when it is unavailable.

Before running on the field, measure the OTOS mount offset and linear/angular scalars in `apps/otos_stream.cpp` on the Pi. Confirm with the robot on blocks that pushing forward increases Override X, pushing right increases Y, and a clockwise turn increases heading. Test that disconnecting the Pi changes the pose source while pose based motion continues from tracking wheels. The existing camera target packets are ignored by the odometry reader.

## Debug GUI test

`TESTING_AUTONOMOUS` remains enabled in `include/aon/constants.hpp`, which selects `GuiDebug` and leaves driver control inactive during this test mode. Open **DEBUG → DATA** to see `OTOS live` (1 for fresh packets), `Pose source` (0 none, 1 motor, 2 tracking, 3 OTOS, 4 tracking plus OTOS), X, Y, and heading. **Live Graph** plots X against Y; **Field Map** records pose samples while a position source works. The **Auton Runner** shows `NO POSITION` and `WAIT` only when all position sources fail. Its RESET button reanchors the current sensor readings to the configured initial pose.

For incremental movement testing, select **DEBUG → Registered Autons → OTOS Square Builder**, then open **VARS**. The checked-in steps are Move 1 (45 inches), Turn 1 (0 degrees), Move 2 (0 inches), Turn 2 (0 degrees), and Move 3 (0 inches). Adjust a value with the GUI buttons; a zero step is skipped. Return to **Auton Runner** and press **RUN**. The turns are relative, with positive degrees clockwise. Press **RESET** before a new run if you want the robot's current position to be field pose (0, 0, 0). To test fallback, run with OTOS present, then disconnect its packet stream and verify `Pose source` changes to 2; disconnect tracking wheels only on blocks and verify it changes to 3 or 1 as available.

## OTOS and V5 IMU heading

Override calibrates the V5 IMU at startup while the robot is still. Tracking wheels and OTOS update X/Y as available, while the V5 IMU supplies the heading used by autonomous. Its uneven steps are smoothed over about 0.02 seconds. If the IMU is unavailable, heading comes from tracking wheels, then motor encoders, then OTOS. A returning IMU is aligned to the current pose without a jump. Every GUI RESET establishes a new heading origin without moving the reported pose.

In **DEBUG → DATA**, compare `Heading (deg)` (V5 IMU based), `OTOS H (deg)` (unfiltered OTOS), and `IMU heading` (1 when the latest update used the V5 IMU). Leave the robot still for a minute; `Heading (deg)` should remain near zero even if `OTOS H (deg)` creeps. Then turn it clockwise and check that both increase. The smoothing time is set by `V5_IMU_HEADING_SMOOTHING_SECONDS` in `include/aon/constants.hpp`; 0.02 seconds is a starting value. The V5 IMU can drift too, so compare both sensors while stationary. The Pi's OTOS angular scalar and mounting offset still need robot-specific calibration. The selected X/Y estimate can still drift if its position sensors drift or the wheels slip.

`drivetrain.move()` sends the same profiled RPM to both sides; it uses the selected position source to stop at the requested distance and does not steer from heading. `drivePID()`, `driveAngleOfArc()`, `turn()`, `goToPose()`, and `follow()` also use the selected pose or heading. Run the first move alone after **RESET** and compare `Heading (deg)` with `OTOS H (deg)` in **DEBUG → DATA**. If the physical robot turns while the heading readings stay near zero, check sensor mounting and IMU port. `turn()` and `goToPose()` still use heading feedback.
